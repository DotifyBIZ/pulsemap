# Pulsemap — Instructions for AI Agents

Pulsemap is developed by Dotify. It follows Dotify's internal engineering standards, restated below in project-specific terms — this file is self-contained; it doesn't link back to Dotify's internal engineering-system host, since this repo is public and that host isn't.

## Two rules that override your defaults

**1. You are a tool, not an author.** Never add `Co-Authored-By` trailers naming an AI model, "Generated with..." tags, or any agent attribution to commits, PR descriptions, changelog entries, or code comments. The person who directed the work is the author and is accountable for it — this applies to every contributor, not just Dotify staff.

**2. Never scaffold a new top-level directory or restructure existing ones without asking first.** Propose the actual tree and wait for confirmation. If a human changes what you proposed, record why in `docs/adr/`.

## Before writing code

- **Read `docs/adr/` first.** Significant decisions — and why alternatives were rejected — are recorded there, not just in commit history.
- **Nullable reference types are enforced.** Never suppress a nullability warning with `!`. Express null-safety through types; handle `null` explicitly.
- **Async all the way down.** Never block on a `Task` with `.Result` or `.Wait()` — this deadlocks the UI thread. Accept and propagate a `CancellationToken` on every async I/O method.
- **`Pulsemap.App.Core` has zero WinUI/Windows App SDK dependency.** Business logic, models, and services live there and must compile without it. Platform-specific capabilities (e.g. WLAN adapter access) go behind interfaces in Core's `Abstractions/`, implemented only in `Pulsemap.App`.
- **MVVM, no logic in code-behind.** Code-behind wires views; decisions belong in view models and services.
- **Dispose what you open.** Use `using` declarations; types holding disposable fields implement `IDisposable`. `HttpClient` is the one exception — inject via `IHttpClientFactory`, never instantiate per call.
- **Exceptions are for the exceptional.** Expected outcomes (a missing record, an unmeasurable band) return a result, not a thrown exception. Never leave a catch block empty.
- **Money is `decimal`, distance/RF math is `double`** — don't mix them up.
- **Colors and type come from the design tokens**, not hand-picked hex values — see `docs/design-tokens.md`. They live inlined in `App.xaml`'s `ResourceDictionary`, not a separate merged file — see the XAML compiler note below for why.
- **XAML compiler quirks (WindowsAppSDK.WinUI 2.3.6, observed 2026-09-01):** A standalone `.xaml` file whose root element is `ResourceDictionary` may fail with a cryptic `WMC9999 "cannot find Polish/neutral culture resources"` error — this is the XAML compiler's own error-reporting path breaking on a non-English OS locale, not a real problem with your markup, and it can mask a genuinely different underlying error. If you hit `WMC9999`, don't trust it as the real problem: temporarily move suspect files fully outside the project directory (renaming within the tree isn't enough — the SDK's XAML globbing is recursive and folder-name-independent) to bisect down to the actual cause. Concretely already found: (1) an extra `ResourceDictionary`-rooted file caused it once a `Page`-rooted file was *also* present and broken — inlining resources into `App.xaml` (which is `Application`-rooted and always compiled first) sidesteps it; (2) `{x:Bind Some.Method('literalArg')}` — the function-call-with-string-literal-argument form of x:Bind — is not supported by this compiler version and triggers the same masked error; use a computed property on the bound type instead; (3) `{x:Bind PageRoot.ViewModel.SomeCommand}` inside a nested `DataTemplate` — binding to an outer named element's property path from within a `DataTemplate`'s own `x:DataType` scope — also isn't supported here; fall back to a plain `Tag="{x:Bind}"` (binds the template's own DataContext, which *is* supported) plus a code-behind `Click` handler that calls the command directly.
- **Related but distinct — a runtime (not compile-time) XAML crash:** declaring `IsChecked="True"` on a `ToggleButton` in markup throws `Microsoft.UI.Xaml.Markup.XamlParseException: Failed to assign to property 'Microsoft.UI.Xaml.Controls.Primitives.ToggleButton.IsChecked'` the moment that page is constructed (`LoadComponent`), silently killing the app since it happens inside `async void`/fire-and-forget navigation code with nothing to catch it. Same locale-masked-error family (the exception's primary message is unreadable Polish mojibake; only a secondary fallback line names the real property), but this one fires at `InitializeComponent()` time, not build time — so it won't show up until the page is actually navigated to. Fix: don't set `IsChecked` declaratively; set it in code-behind after `InitializeComponent()` instead (e.g. `SomeToggleButton.IsChecked = true;`). If a page like this crashes the app with no visible error, temporarily wire `Application.UnhandledException` to write `e.Exception.ToString()` to a file — the default unhandled-exception behavior here is silent process termination with nothing in the UI.
- **`x:Bind TwoWay` on `TextBox.Text` defaults to `UpdateSourceTrigger=LostFocus`, not `PropertyChanged`.** This bit us for real: a wizard step's "Next" button stayed disabled after typing a value and clicking straight to "Next" without tabbing away first — the ViewModel property was still empty because the TextBox never lost focus to flush the binding. Any TwoWay-bound `TextBox.Text` that gates a `CanExecute` (or is read immediately after by other logic) needs `UpdateSourceTrigger=PropertyChanged` explicitly: `Text="{x:Bind ViewModel.Foo, Mode=TwoWay, UpdateSourceTrigger=PropertyChanged}"`. `CheckBox.IsChecked`, `ComboBox.SelectedItem`, and `NumberBox.Value` all commit immediately on their own interaction and don't need this.
- **`Pivot` silently clips overflowing headers into a scroll strip** (small `‹›` chevrons) once header text is too wide for the host column — a clipped-away `PivotItem` is not click-reachable at its "logical" screen position even though `FindFirst`-by-name still returns a seemingly valid `BoundingRectangle` for it (UI Automation doesn't know it's visually clipped). If a Pivot has 3+ items in a narrow side panel, size the column generously and keep header text short, or the last tab(s) become effectively unreachable by mouse.

## Non-negotiable, every change

- No secrets in code or version control — ever, including test fixtures.
- Validate input at every boundary: file parsing (floor plan images/PDFs, project bundles), WLAN adapter data, CLI/user input.
- Business logic (`Pulsemap.App.Core`) carries tests — minimum 80% branch coverage. UI projects are exempt from that bar but still need meaningful tests for view model logic.
- Dependencies are pinned, with a committed lockfile.
- New markdown docs, ADRs, and templates follow the existing structure in this repo — don't invent a new documentation convention.

## When unsure, stop and ask

Don't invent a convention to fill a gap. Name what's missing, propose the smallest reasonable option, and ask. A wrong convention adopted silently is far more expensive to undo than a question would have been.

## Project

- **What this is:** Pulsemap — a local-first WiFi site survey and planning tool. See `README.md`.
- **Structure preset:** Adapted from Dotify's `desktop-winui` preset — `src/Pulsemap.App` (WinUI 3 shell, unpackaged) + `src/Pulsemap.App.Core` (platform-free engine) + `tests/Pulsemap.App.Core.Tests` + `tests/Pulsemap.App.Tests`, wired into `Pulsemap.sln`.
- **Run locally:** `dotnet build Pulsemap.sln` then run `src/Pulsemap.App/bin/<config>/<platform>/<tfm>/<rid>/Pulsemap.App.exe`, or `dotnet run --project src/Pulsemap.App` on a machine with a display (this app needs an interactive Windows session — it won't launch headless).
- **Run tests:** `dotnet test Pulsemap.sln`. `Pulsemap.App.Core.Tests` has real coverage (~90% branch as of 2026-09-01, enforced in CI) — 57 tests as of the logging/floor-plan-rendering work. `Pulsemap.App.Tests` (added 2026-09-01) covers `WorkspaceViewModel`, `NewSurveyWizardViewModel`, `HomeViewModel`, `SurveysViewModel`, and the App-layer services — 59 tests using hand-rolled fakes in `Fakes/` for App-layer service interfaces rather than a mocking library (small interfaces, no new dependency needed). Notably includes a regression test for a real bug (`ConfirmWalkPointCommand` staying permanently disabled after starting a guided walk, because `CurrentWalkPoint`'s setter didn't notify the command's `CanExecute` — found via manual UI automation, not by a test, the first time), and `FloorPlanImageCacheTests` genuinely exercises PDFium/SkiaSharp rasterization rather than mocking it, since the whole point of that test is confirming the native dependency actually works unpackaged on a real machine, not just that the C# call compiles.
- **Verify before committing:** `dotnet format Pulsemap.sln --verify-no-changes`, `dotnet build Pulsemap.sln --configuration Release`, `dotnet test Pulsemap.sln --configuration Release`.
- **Deployed by:** GitHub Releases, InnoSetup-built installer wrapping the self-contained `WindowsAppSDKSelfContained` publish output (see `docs/adr/0002-installer-innosetup-over-msix.md`). **CI/release pipeline (added 2026-09-01):** `.github/workflows/ci.yml` runs format/build/test on `windows-latest` for PRs into `main`/`staging` and pushes to `main`; `.github/workflows/release.yml` runs semantic-release (config in `.releaserc.json`) on push to `main` only — reflects the intended `feature -> staging -> main` flow, where landing on `main` is what cuts a release. The release workflow now attaches the InnoSetup installer to the GitHub Release it creates: `Pulsemap.iss` (real-compiled and installed with Inno Setup 7 locally; per-user install under `{localappdata}`, no admin needed, unsigned per the open code-signing decision) is committed, and `scripts/build-installer.ps1` — invoked by `@semantic-release/exec`'s `prepareCmd` once semantic-release has computed the next version, so it only runs when a release is actually happening — runs `dotnet publish` (locked-mode restore) then `ISCC.exe "/DMyAppVersion=<version>" Pulsemap.iss` and writes a `.sha256` checksum sidecar next to it; `@semantic-release/github`'s `assets` config (glob-matched) uploads both to the release. Confirmed empirically rather than assumed: `windows-latest` now resolves to the Windows Server 2025 image, which dropped the Inno Setup preinstall the older Server 2022 image had (checked against `actions/runner-images`) — so the `release` job `choco install`s a version-pinned Inno Setup itself instead of relying on it being there, and moved from `ubuntu-latest` to `windows-latest` in the process, since it now also runs the real WinUI3 publish, not just semantic-release. `@semantic-release/exec` (`7.1.0`) added to `package.json`/`package-lock.json` for this — audited clean, 0 vulnerabilities. `package.json` exists only to run semantic-release (not a Node project); `package-lock.json` is committed (`semantic-release` pinned at 25.0.9 after bumping past a 24.x with 18 known CVEs in its bundled npm-publish code path — 0 vulnerabilities now), so `release.yml` uses `npm ci`. **First real CI run (2026-09-01) failed** with `NETSDK1094` — root cause and fix in commit `a23b755`: `Pulsemap.sln`'s "Any CPU" solution config silently mapped `Pulsemap.App` to `Platform=x86` (a template leftover) while `RuntimeIdentifier` auto-detects `win-x64` from the machine's process architecture; building through the .sln without an explicit `-p:Platform=` therefore built x86 against a win-x64-only restore. Fixed by remapping Any CPU -> x64 in the .sln directly, so `dotnet build Pulsemap.sln` (no flags — matches CLAUDE.md's own documented commands) now resolves consistently everywhere. **Second CI failure (also `NETSDK1094`, different root cause):** Release builds failed with "Unable to optimize assemblies for performance: a valid runtime package was not found" — `Pulsemap.App.csproj`'s template-default `PublishReadyToRun=True` for Release needs a win-x64 crossgen/ReadyToRun runtime pack that isn't in `packages.lock.json`, and CI's locked-mode restore has no local NuGet cache to mask the gap the way local builds had been. Turned off (same treatment `PublishTrimmed` already got) rather than chased — pure cold-start-perf optimization with no functional effect, and not yet exercised by anything in this repo's actual release pipeline.
- **Built so far:** the full Core engine (models, zip+JSON persistence, propagation model, Kriging interpolation, AP placement, CSV/JSON/PDF export, coverage-grid calculation, WLAN abstractions, guided-walk measurement point suggestion and capture), the app shell (DI, NavigationView, Mica, HomePage), the New Survey wizard, and the Workspace page (`FloorPlanCanvas`: walls/test points/APs/heatmap rendering, tool-mode editing with auto-save, Coverage/Suggestions/Adapter side panel). `WlanAdapterService` (native `wlanapi.dll` P/Invoke — see the plan's research notes on why the WinRT `Windows.Devices.WiFi` API won't work unpackaged) is done and real-hardware-verified, including the guided measurement walk end to end (Adapter tab: pick candidate points, "Start Guided Walk" → walk there → "Confirm Arrival & Capture" → advance, with a purple target marker on the canvas). Live band detection was deliberately NOT duplicated into the wizard's Adapter & Bands step — that step already says detection happens in the Workspace, where WLAN access actually lives. `GreedyCoverageApPlacementOptimizer` now ranks each band's candidate channels by measured interference before round-robin-assigning them across APs (zero measurements reproduces the old fixed-order behavior exactly, via a stable sort). Still open: making coverage *reliability* itself (the -67dBm placement threshold) measurement-aware — deliberately left out as a bigger, more speculative design (would need interpolating sparse TestPoint interference across the denser placement grid) than the channel-ranking piece just built.
- **Guided measurement walk (PM requirement, added 2026-09-01, DONE):** the app suggests measurement points (`MeasurementPointSuggester`, reusing the shared `FloorGrid` candidate-grid logic at a 3m walking spacing), the surveyor walks to each and confirms arrival, the app captures the reading (`TestPointCapture`) and advances. Every point captures background noise/interference (full BSS list, not just the target network, stored as `TestPoint.InterferenceReadings`); existing-network audits (`Survey.TargetNetworkSsid`, set in the wizard's Basics step) also capture the target network's own signal per band in `TestPoint.Measurements` — new-deployment surveys skip this, since there's no live network yet. Verified with a full real run against this machine's actual adapter: captured points correctly split target-network signal per band and a real neighboring-BSS interference list, round-tripped through save/load. Not yet done: feeding the captured interference back into AP placement's channel/power suggestions (build-order item 10 — `GreedyCoverageApPlacementOptimizer`/`ChannelPlan`).
- **Floor plan image/PDF background rendering (added 2026-09-01, DONE):** image-style surveys previously saved/loaded their picked floor plan but never drew it — `FloorPlanCanvas` only rendered walls/points/APs/heatmap as vector shapes. Now renders both PNG/JPG and PDF backgrounds. WinRT's own decode APIs (`Windows.Graphics.Imaging`, `Windows.Data.Pdf`) are on Microsoft's package-identity-required list and don't work unpackaged here — same failure family as the `ApplicationLanguages`/`ResourceContext` footguns already documented above, confirmed against Microsoft's own API list rather than assumed. Used instead: a new `FloorPlanImageCache` (App layer) writes the floor plan to a cached local PNG (PDF pages rasterized via the new `PDFtoImage` package, which wraps PDFium/SkiaSharp and explicitly lists WinUI 3 as supported), and `FloorPlanCanvas` loads that file via `BitmapImage`'s file-`Uri` path — the standard unpackaged-safe pattern, not a WinRT API. `FloorPlanImageCacheTests` genuinely exercises PDFium rasterization on a real machine rather than mocking it, since that native dependency working at all was the actual open question. `Render` is now `RenderAsync`; a render superseded by a newer one while still decoding abandons itself, since `FloorChanged` fires on nearly every floor edit.
- **CSV/JSON/PDF export wired to UI (added 2026-09-01, DONE):** `ISurveyDataExporter`/`IReportExporter` were fully built and tested since early in the project but had no ViewModel or XAML calling them — unreachable from the app. Now a title-row "Export" button + `MenuFlyout` on the Workspace page (first use of `MenuFlyout` in this app — deliberately not a 4th `Pivot` tab, given the documented Pivot-clipping footgun above) drives all four export kinds via a new `ISurveyExportFilePickerService` (wraps `FileSavePicker` the same way `FloorPlanFilePickerService` already wraps `FileOpenPicker`).
- **Local diagnostic log file, not telemetry (added 2026-09-01, DONE — see `docs/adr/0003-local-diagnostic-logging.md`):** `IAppLogger`/`FileAppLogger` (`Pulsemap.App.Core/Logging/`) writes ERROR/WARN/INFO lines to `%LocalAppData%\Pulsemap\Logs\pulsemap-{date}.log`. No network calls anywhere — Settings has an "Open Logs Folder" button (`Windows.System.Launcher.LaunchFolderPathAsync`) so a user can find and manually share the file themselves. Wired into every previously-silent catch block across the app, plus a best-effort addition alongside (not replacing) the existing raw crash-file write in `App.xaml.cs`'s `UnhandledException` handler.
- **Surveys library page (added 2026-09-01, DONE):** the `NavSurveys` ("Badania") nav tab was a dead stub (`// Not built yet`) — clicking it did nothing. Home previously showed every survey with no cap, so there was nothing left for a dedicated Surveys page to add; per a product decision, Home is now a dashboard (greeting + New Survey CTA + the 3 most recent surveys only, `HomeViewModel.RecentSurveysLimit`), and the new `SurveysPage`/`SurveysViewModel` owns the full, unlimited list plus rename and delete (each behind a `ContentDialog` confirm — this app's first use of `ContentDialog`). Rename changes `Survey.Name` in the persisted file in place via the existing `ISurveyFileService.SaveAsync` — it does not touch the filename on disk, which was never derived from the display name after creation anyway. `ISurveyLibraryService` gained `DeleteAsync`/`RenameAsync`. Per-card Rename/Delete buttons use `Tag="{x:Bind}"` + a code-behind `Click` handler rather than binding `Command` directly inside the `GridView`'s `DataTemplate`, per the documented nested-`DataTemplate`-binding XAML compiler quirk above.
- **Live manual QA pass (2026-09-01):** the app's own developer did a real click-through (not automation) and found two real bugs, both fixed same-day: (1) the dead Surveys tab above; (2) Settings' "Open Logs Folder" button silently did nothing on a fresh install, because `FileAppLogger` only creates its log directory lazily on first write, and `Launcher.LaunchFolderPathAsync` fails on a path that doesn't exist yet — fixed at the call site (`SettingsViewModel.OpenLogsFolderAsync` now `Directory.CreateDirectory`s before launching) rather than inside `FileAppLogger` itself, since creating the directory eagerly in `FileAppLogger`'s constructor would have broken an existing `FileAppLoggerTests` case that deliberately blocks the log path with a plain file to prove the logger degrades gracefully when its directory can't be created. The floor-plan image/PDF rendering and the 4 Export buttons weren't specifically called out as broken or working in this pass — still not explicitly confirmed either way, unlike the two bugs above.
